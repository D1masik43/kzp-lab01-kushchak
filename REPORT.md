# Звіт до лабораторної роботи № 5

## 1. Тема, номер і варіант

- Тема: параметризоване сховище, власний виняток і CSV-експорт через рефлексію.
- Предметна область: варіант 17 — «Спортивна ліга» (незмінний з лаб. 1).
- Операційна система: Linux (Debian 13), Java 21, Maven 3.9.9.

## 2. Мета роботи

Завершити Java-частину наскрізного продукту: замінити пряме зберігання
даних у списку на параметризоване сховище `Repository<T>`, додати власний
виняток `DataStorageException` із ланцюгом причин, описати CSV-стовпці
анотацією `@CsvColumn` і реалізувати універсальний експортер, який читає
метадані рефлексією. Дані записуються й читаються через `Path`/`Files` з
явним UTF-8; round-trip тестом доведено, що відновлені об'єкти рівні
початковим.

## 4. `Repository<T>`

Файл: `src/main/java/ua/lpnu/kzp/Repository.java` — `public final class
Repository<T>`. Параметр типу `T` виключає `raw type`: `Repository<MatchRecord>`
приймає лише `MatchRecord`, перевірка типів виконується компілятором без
приведень.

Методи:

- `add(T item)` — додає запис, відхиляє `null` через `Objects.requireNonNull`.
- `all()` — повертає **незмінний знімок** (`List.copyOf`) у порядку
  додавання; подальші виклики `add` на вже отриманий знімок не впливають
  (перевірено тестом `allSnapshotDoesNotReflectLaterAdditions`).
- `find(Predicate<? super T> condition)` — повертає записи, що задовольняють
  умову; `? super T` дає змогу передати предикат, написаний для супертипу.

## 5. Модель даних — `MatchRecord`

Варіант 17: `MatchRecord(homeTeam: String, awayTeam: String, date:
LocalDate, homeScore: int, awayScore: int, round: int)`.

Інваріанти конструктора: назви команд не `null` і не порожні (`"порожня
назва команди"`), рахунок невід'ємний (`"від'ємне числове значення"`), тур
не менше 1 (`"тур має бути не менше 1"`), дата не `null`. Ці самі тексти
помилок уже використовувались у `Match`/`ScheduledMatch` лаб. 1-4 —
узгоджена термінологія в усьому проєкті.

`equals`/`hashCode` порівнюють усі шість полів (`Objects.hash`) — необхідна
умова для коректного round-trip `assertEquals(original, restored)` на
списках.

## 6. `@CsvColumn`: Retention, target, назви й порядок стовпців

```java
@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface CsvColumn {
    String value();
}
```

`RUNTIME` лишає анотацію доступною для `getAnnotation` під час виконання
(без цього `CsvExporter` не знайшов би її); `FIELD` обмежує застосування
полем. Анотація лише описує контракт — не виконує експорт сама.

Поля `MatchRecord` і їхні стовпці: `homeTeam → "Господарі"`, `awayTeam →
"Гості"`, `date → "Дата"`, `homeScore → "Рахунок господарів"`, `awayScore →
"Рахунок гостей"`, `round → "Тур"`.

**Порядок стовпців у файлі визначається сортуванням імен Java-полів**, а не
порядком оголошення чи порядком полів у варіанті (методика лаб. 5, розділ
«Варіанти завдань»). Відсортовані імена полів `MatchRecord`: `awayScore,
awayTeam, date, homeScore, homeTeam, round` — тому фактичний заголовок
файла:

```
Рахунок гостей,Гості,Дата,Рахунок господарів,Господарі,Тур
```

Цей порядок навмисно не збігається з природним порядком читання
(«господарі, гості, дата, рахунок...») — перевірено тестом
`headerColumnsAreOrderedByJavaFieldName`, щоб зміна порядку оголошення полів
у майбутньому одразу проявилась у тесті.

## 7. Рефлексивний експортер

`CsvExporter.write(Path path, Class<T> type, List<? extends T> records)`:

1. `Arrays.stream(type.getDeclaredFields())` — усі поля класу.
2. `.filter(isAnnotationPresent(CsvColumn.class))` — лишає лише анотовані.
3. `.sorted(Comparator.comparing(Field::getName))` — детермінований порядок.
4. Для кожного поля — `field.trySetAccessible()`; відмова перетворюється на
   `DataStorageException`, а не ігнорується.
5. Заголовок і кожен рядок будуються одним і тим самим списком полів, тому
   позиції значень завжди узгоджені з заголовком.
6. Запис — `Files.writeString` з `StandardCharsets.UTF_8` і
   `TRUNCATE_EXISTING`, щоб хвости попереднього (довшого) експорту не
   лишались у файлі.

Експортер не знає класу `MatchRecord` наперед, не викликає геттери
конкретного домену й не містить розгалуження за типом — працює з будь-яким
класом, де є хоча б одне поле `@CsvColumn` (інакше — `DataStorageException`,
перевірено тестом `writeThrowsWhenClassHasNoCsvColumns`).

## 8. Формат CSV

Повний заголовок (`data/matches.csv`, згенеровано самим `CsvExporter`):

```
Рахунок гостей,Гості,Дата,Рахунок господарів,Господарі,Тур
0,Шахтар,2026-03-01,3,Динамо,1
1,"Верес ""Б""",2026-03-02,1,"Карпати, Львів",1
2,Металіст,2026-03-08,2,Зоря,2
1,Полісся,2026-03-09,4,Оболонь,2
3,Колос,2026-03-15,0,Рух,3
```

Рядок 2 ілюструє екранування: поле `Карпати, Львів` містить кому, а поле
`Верес "Б"` — лапку (подвоєну всередині лапок за правилом CSV) — обидва
взяті в подвійні лапки. Кодування — UTF-8 явно і при записі
(`Files.writeString`), і при читанні (`Files.readString`).

## 9. Імпорт і round-trip

Алгоритм відновлення (тест `roundTripRestoresEqualObjectsIncludingEscapedField`):

1. `CsvExporter.write(path, MatchRecord.class, original)`.
2. `Files.readString(path, UTF_8)` — увесь текст документа.
3. `CsvParser.parseDocument(text)` — документний парсер (не `split(",")`,
   бо він розділив би поле `"Карпати, Львів"` всередині лапок).
4. `rows.stream().skip(1).map(MatchRecord::fromFields)` — перший рядок
   (заголовок) пропускається, решта розбираються за позиціями у
   відсортованому порядку полів (розділ 6).
5. `assertEquals(original, restored)` — порівняння списків через `equals`
   `MatchRecord` (усі шість полів, включно з `LocalDate` і екранованими
   текстовими полями).

Ключ демонстрації round-trip для варіанта 17 — `homeTeam + awayTeam + date`
(наприклад, `Карпати, Львів` + `Верес "Б"` + `2026-03-02`).

## 10. Помилки

| Рівень | Приклад | Реакція |
|---|---|---|
| Модель | порожня назва команди, від'ємний рахунок, тур < 1 | `IllegalArgumentException` у конструкторі `MatchRecord` |
| Формат | неправильна кількість CSV-полів (не 6) | `DataStorageException` ("Очікується 6 полів") |
| Значення | нечислове поле рахунку/туру | `DataStorageException` із `cause` — `NumberFormatException` |
| Значення | некоректна дата | `DataStorageException` із `cause` — `DateTimeParseException` |
| Рефлексія | клас без жодного `@CsvColumn` поля | `DataStorageException` ("не має CSV-полів") |
| Файл | батьківська тека існує як звичайний файл (не директорія) | `DataStorageException` із `cause` — `IOException` |

Жоден рівень не поглинається порожнім `catch`: кожна гілка або формулює
власне повідомлення, або передає причину далі через `getCause()` —
перевірено тестами (`fromFieldsRejectsNonNumericScore`,
`writeWrapsFileSystemErrorWithCause` тощо).

## 16. Відповіді на контрольні питання

1. Параметр типу в `Repository<T>` розв'язує проблему типобезпеки без
   дублювання коду сховища для кожного класу: без нього довелось би або
   писати окремий `MatchRecordRepository`, `BookRepository` тощо для
   кожного домену, або використовувати `Object` і втратити перевірку типів
   компілятором.
2. Параметризований клас (`Repository<MatchRecord>`) перевіряє типи під час
   компіляції й не вимагає приведень при читанні; `raw type` (`Repository`
   без аргументу) вимикає цю перевірку — компілятор дозволить додати об'єкт
   будь-якого типу, а помилка проявиться лише під час виконання як
   `ClassCastException`.
3. `Predicate<? super T>` у `find` дозволяє передати умову, написану не
   лише для `T`, а й для будь-якого його супертипу (наприклад,
   `Predicate<Object>`) — це розширює список предикатів, які можна
   використати, не звужуючи безпеку (контраваріантність параметра, який
   лише приймає `T`, а не повертає його).
4. `all()` має повертати незмінний знімок (`List.copyOf`), бо інакше
   зовнішній код, отримавши внутрішній список, міг би додавати чи видаляти
   елементи в обхід `add()` — сховище втратило б контроль над власним
   станом (саме цю властивість перевіряє тест
   `allSnapshotDoesNotReflectLaterAdditions`).
5. Checked exception (`DataStorageException extends Exception`) — виняток,
   який компілятор вимагає або обробити `catch`, або оголосити в `throws`;
   доречний тут, бо помилки CSV, рефлексії чи файлової системи — очікувані
   стани предметної області (хибний вхідний файл), про які виклик коду
   зобов'язаний знати й свідомо вирішити, як реагувати.
6. Причина (`cause`) власного винятку зберігає початкову технічну помилку
   (`IOException`, `NumberFormatException`, відмову рефлексії) під зрозумілим
   доменним повідомленням — `getCause()` дає змогу відлагодити справжню
   причину, не втрачаючи зручного повідомлення найвищого рівня.
7. `Path` і `Files` будують шлях, коректний для конкретної ОС (роздільник
   `/` чи `\`), і не схильні до помилок конкатенації рядків (зайвий чи
   відсутній роздільник); `Path.of("target", "data", "records.csv")`
   завжди правильний незалежно від платформи, на відміну від
   `"target" + "/" + "data" + "/" + "records.csv"`.
8. Кодування потрібно задавати явно і при записі, і при читанні, бо інакше
   обидві операції використовують кодування за замовчуванням операційної
   системи (`file.encoding`), яке відрізняється між Windows (часто
   `windows-1251` для кирилиці) і Linux/macOS (`UTF-8`) — без явного
   `StandardCharsets.UTF_8` текст, записаний на одній ОС, прочитається
   пошкодженим на іншій.
9. `@Retention(RUNTIME)` зберігає анотацію в байт-коді й доступною для
   рефлексії під час виконання програми (без неї компілятор прийняв би
   анотацію, але `getAnnotation` під час виконання повернув би `null`);
   `@Target(FIELD)` обмежує місця, де анотацію дозволено застосовувати,
   лише полями класу — компілятор відхилить спробу позначити нею метод чи
   клас.
10. Анотація — це лише метадані, прикріплені до елемента програми; вона не
    містить виконуваного коду й не може сама нічого записати чи прочитати.
    Експорт виконує окремий код (`CsvExporter`), який рефлексією читає
    анотацію й вирішує, що з нею робити — анотація лише описує контракт
    («це поле — CSV-стовпець із такою назвою»).
11. `getDeclaredFields()` повертає всі поля класу, оголошені безпосередньо в
    ньому, незалежно від модифікатора доступу (`private`, `protected`,
    `public`) і без полів успадкованих класів; метод для публічних полів
    (`getFields()`) повернув би лише `public`-поля, але також успадковані
    від батьківських класів — для `MatchRecord` із приватними полями
    підійшов лише `getDeclaredFields()`.
12. `trySetAccessible()` потрібно перевіряти, бо приватне поле за
    замовчуванням недоступне для читання ззовні класу через рефлексію;
    виклик повертає `true`/`false` замість винятку, і якщо модуль чи
    `SecurityManager` заборонили доступ, код свідомо перетворює відмову на
    власний `DataStorageException`, а не отримує неочікуваний
    `InaccessibleObjectException` далі за стеком.
13. Порядок полів для CSV має бути детермінованим, бо `getDeclaredFields()`
    не гарантує порядок оголошення (JVM може повернути поля в довільній
    внутрішній послідовності) — без явного сортування за іменем той самий
    клас міг би дати різний порядок стовпців між запусками чи між версіями
    JVM, і заголовок розійшовся б зі значеннями.
14. `split(",")` розділяє рядок за кожною комою безумовно, тому поле
    `"Карпати, Львів"` у лапках розпалося б на два окремі поля `"Карпати`
    і ` Львів"` — загальний CSV-парсер мусить відрізняти кому-дані
    (всередині лапок) від коми-роздільника (поза лапками), що потребує
    машини станів, а не простого розбиття рядка.
15. Поле, що містить кому, лапку або перенесення рядка, оточується
    подвійними лапками; подвійна лапка всередині такого поля подвоюється
    (`"` → `""`) — наприклад, `Верес "Б"` записується як `"Верес ""Б"""`.
16. Порожній список потребує окремого параметра `Class<T>`, бо без жодного
    запису неможливо визначити тип `T` і, відповідно, його анотовані поля
    через рефлексію самого списку (порожній `List<T>` не містить інформації
    про клас елементів під час виконання через стирання типів) — `Class<T>`
    передається явно саме для побудови заголовка в цьому випадку.
17. Універсальний експортер (`CsvExporter`) не знає жодного конкретного
    класу й визначає стовпці лише рефлексією над анотаціями — працює з
    будь-яким класом; предметний `fromCsv` (`MatchRecord.fromCsv`), навпаки,
    знає точний тип і порядок полів свого класу та виконує власну
    валідацію (діапазони значень, формат дати), яку універсальний код не
    може знати наперед.
18. Програма розрізняє рівні помилок: модель (інваріанти конструктора,
    `IllegalArgumentException`), формат (кількість CSV-полів), значення
    (нечисле поле чи хибна дата), файл (помилки файлової системи) і
    рефлексія (клас без анотованих полів чи заборонений доступ) — кожен
    рівень має власне зрозуміле повідомлення (розділ 10).
19. Тест round-trip (`roundTripRestoresEqualObjectsIncludingEscapedField`)
    доводить, що послідовність «об'єкт → CSV → читання → об'єкт» не губить
    і не спотворює дані: відновлені об'єкти рівні початковим за `equals`
    (усі поля, включно з екранованими комою й лапкою в текстовому полі).
20. Порожній `catch (Exception e) { return List.of(); }` не можна
    використовувати, бо він приховує різницю між «файл відсутній»,
    «файл пошкоджений» і «дані коректні, але порожні» — виклик коду не
    дізнається про справжню причину відмови й не зможе відреагувати
    правильно; кожна причина має лишатися розрізненою через власний
    виняток і `cause`.

## 17. Висновки

Java-частина наскрізного продукту завершена: `Repository<T>` замінив прямий
список, `@CsvColumn` і рефлексивний `CsvExporter` дали змогу експортувати
будь-який анотований клас без прив'язки до конкретного домену, `CsvParser`
коректно читає назад поля з комами й лапками, а `DataStorageException`
передає причину помилки, не приховуючи її. Round-trip тестом доведено, що
`MatchRecord`-об'єкти не втрачаються під час запису й читання. Усі 60
тестів лаб. 1-4 лишились без змін, додано 32 нових (разом 92, 0 падінь).
Створений у цій роботі
`data/matches.csv` стає узгодженим UTF-8 входом для наступного програмного
блоку курсу (лаб. 6-7, Python).
